feat(tools): Agent 工具调用能力（Function Calling）+ 联网检索

Researcher 不再被动接受一次性检索结果：它现在可以自己决定「还要不要查、
换个说法再查、还是转去联网」。这是 T3 的目标，也补掉了 README「已知边界」
里"不具备实时联网检索"这条。

## 形状

标准 function calling 循环：模型要求调工具 → 执行 → 以 role=tool 回填 →
直到模型不再要工具 → 关掉 tools、打开 json_mode 收尾要 JSON。

两个工具：`kb_search`（本地知识库）、`web_search`（互联网）。

## 三条守住的东西

1. **默认关闭**（ENABLE_TOOLS / ENABLE_WEB_SEARCH 均 false）。不传 tools 时
   请求形状与之前逐字节一致，40 主题评测基线因此不受影响。开着会多 1~3 轮
   模型调用，成本上升；联网更会随时间变化，一开评测就不可复现。
2. **溯源约束一字不改**。工具返回的是原文（kb 是 chunk 原文、web 是搜索索引
   给出的摘要），模型必须逐字引用，`_verify` 照样做子串匹配。工具只扩大材料
   范围，不放松"每句话都要能回到原文"。
3. **工具失败不抛给编排层**。一律以 ToolResult.ok=False 回给模型，
   让它自己换策略。抛异常会让整章 research 崩掉，而问题往往只是"这个站点抓不到"。

## 两个不报错、只让结果悄悄变错的坑（都已修 + 加测试）

1. **渲染没打 doc_id**：`web_search` 原先只写「[网页1]」，模型就自己编 `web_1`
   当 source_id，全部被溯源校验判成"不在检索结果中"丢弃——网页查到了却一条
   也用不上。改为与 kb_search 一致的 `doc_id=web_xxx` 格式。
2. **工具片段没进证据池**：溯源校验原本只比对预检索片段，模型引用网页时
   会被判成编造。改为 ToolRegistry 收集 + Researcher 合并证据池后再校验。

## 默认搜索源实测结论

起初用 DuckDuckGo HTML 端点（惯例做法），本机实测连接超时；Bing 能连通但返回
JS 渲染的空壳页（抓到的标题与查询无关）。360 可达且返回真实结果，故设为默认，
三档仍可切换。另外 360 的结果链接是 so.com 跳转、单独请求返回 400（反爬），
所以不逐页抓取，直接用结果页的 `data-mdurl` + 摘要——更稳也更快，代价是
拿不到整页正文（已在 README「已知边界」写清）。
