# 阶段三验收记录：评测体系（40 主题 × 3 档 × 跨厂商判官）

环境：Windows 11 / Python 3.12.10 / SQLite / 生成 DeepSeek `deepseek-chat` / 判官 硅基流动 `zai-org/GLM-5.3-Flash`
权威批次：`eval/results/v6/`（120 次观测，全部成功）
总花费：**¥2.75**（生成 ¥2.05 + 判官 ¥0.70），耗时约 70 分钟

---

## 0. 结论

**多 Agent 协作有效，Reviewer 无效。这两个结论现在都有置信区间支撑，而且判官是另一家厂商的模型。**

| 方案 | 要点覆盖率 | 语义支持率 | 未覆盖要点 | 引用归属错 | 单份成本 |
|---|---|---|---|---|---|
| A · 单 Agent 直出 | 72.6% [65.1, 80.0] | 92.2% | 40 条 | **16 条** | ¥0.0055 |
| B · 多 Agent | **80.2%** [73.5, 87.0] | **99.7%** | 28 条 | **1 条** | ¥0.0199 |
| C · 多 Agent + Reviewer | 80.5% [72.7, 88.3] | 98.9% | 26 条 | 2 条 | ¥0.0296 |

配对比较（同主题内比，n=40，95% CI）：

| 对比 | 要点覆盖率 | 语义支持率 |
|---|---|---|
| A → B | **+7.7pp [+1.6, +13.7] ✅** | **+7.4pp [+3.3, +11.6] ✅** |
| A → C | +8.0pp [−1.0, +17.0] ❌ | **+6.6pp [+2.3, +10.9] ✅** |
| B → C | +0.3pp [−7.9, +8.5] ❌ | −0.8pp [−1.9, +0.2] ❌ |

三条可下的判断：

1. **多 Agent 相对单 Agent：覆盖率 +7.7pp、语义支持率 +7.4pp，两个维度都显著。** 代价是 3.6 倍成本。
2. **Reviewer 没有可测量的收益。** 这次用的正是它应该起作用的那把尺子（语义支持率），结果 −0.8pp、CI 跨 0，成本再涨 49%。
3. **A→C 的覆盖率不显著，是因为 C 的方差更大**（CI ±8.7pp vs B ±6.7pp）——Reviewer 打回重写引入了额外的产出波动，却没换来均值提升。

> 上一轮（v3/v4）我说过"显著"又说"还不显著"，两次都不该当结论：一次是样本太小（20 主题），一次是判官就是被测模型本身。这一轮把三件事都补上了，见 §1。

## 1. 这一轮改了什么（前三轮的结论为什么不能用）

| 问题 | 上一轮的状态 | 这一轮的处理 |
|---|---|---|
| 样本量 | 20 主题 × 2 重复，CI ±10pp，A→B 在 v3/v4 之间翻转（+13.4 → +6.2） | **40 主题**（新增 20 个换角度主题），CI 收到 ±6~8pp |
| 判官 | 与生成同模型（DeepSeek），存在自我偏好 | **跨厂商**：硅基流动 `zai-org/GLM-5.3-Flash` |
| 语义抽样 | 每章取前 2 句 → 三档都是 96~97%，**天花板效应，没有区分度** | 定向抽"高风险句"，A 组降到 92.2%，恢复区分度（见 §5） |

另外修掉两个会直接毁数据的实现缺陷：

- **批次指纹撞车**：`task_id` 原用 `run_id[-6:]`，`audit-smoke` 与 `judge-smoke` 截尾都是 `-smoke`，新批次静默复用了旧批次已 DONE 的任务——0.02 秒"跑完"，指标齐全，全是不相干的结果。改成完整 run_id 的哈希。
- **长句被整条丢弃**：抽样正则上限 120 字，单 Agent 的长段落句子一超限就整条不匹配，A 组样本数变成 0、语义支持率被记成 **0%**。那不是"A 更差"，是指标把长句判成不存在。

## 2. 评测集：40 主题 / 141 要点 / 81 错误说法

新增的 20 个主题刻意换角度，不是前 20 个的复述：

`resi-storage`（户用，唯一负增长）· `top-manufacturers`（集中度）· `aux-service`（辅助服务）· `project-finance`（投融资）· `subsidy-policy`（补贴/容量补偿/租赁）· `cell-cost`（电芯成本传导）· `northwest-grid`（西北集群）· `shared-storage`（共享储能）· `lithium-dominance`（锂电边界）· `fire-safety`（事故时间特征）· `pcs-upgrade` · `emc-model` · `spot-market` · `overcapacity` · `us-market` · `eu-me-market` · `export-scale` · `new-install-record` · `outlook-2026` · `policy-quota`

标注全部由脚本从事实表生成，并做了机器校验：

- 141 条 `must_cover` **全部**能在其 `must_cite` 文档中逐字找到（校验前有 5 条不满足，已补文档）
- 81 条 `forbidden` **无一条**出现在语料里（否则标注自相矛盾）
- 章节数 3/4/5 分布 19/19/2，要点数 3/4/5 分布 21/17/2

`forbidden` 统一用「数字近似错误」（8.4→9.1GWh、96.5%→86.5%），不用方向性错误——方向错了太容易被识破，近似错误才真正考验有没有核对原文。

## 3. 判官：跨厂商，以及踩到的三个坑

`LLM_JUDGE_BASE_URL / MODEL / API_KEY / PRICE_* / EXTRA_JSON` 五项配置，判官可以和生成完全分离。

**坑 1：默认开思考链，单次判定 70 秒。** GLM-5.3-Flash 是推理模型，判一次引用要 70 秒、烧 2000 completion token。
**坑 2：`enable_thinking: false` 被该端点忽略。** 传了也没用，`completion_tokens` 仍是 1987。
只有 `reasoning_effort: "low"` 真正生效：同一条 prompt 从 13.6s/245tok 降到 3.2s/59tok。现在配置里两个都传。
**坑 3：并发会被打限流。** judge 与 audit 并行发两个请求，排到 60 秒后被服务端直接断连（12 次调用里 3 次超时/断连）。改回串行后，均 8 秒、零失败。

还有一条是提前防住的：`doctor` 现在单独体检判官。跨厂商却没填独立 key 时**直接拦下**——否则会拿 DeepSeek 的 key 去请求硅基，240 例全部 ERROR，等两小时后才发现。

## 4. 指标口径

| 指标 | 计算 |
|---|---|
| 要点覆盖率 | LLM judge 逐条判定 `must_cover` 是否被正文明确主张（语义等价即可，数字必须对得上） |
| 语义支持率 | 抽样断言，判官给该 doc_id 的**整篇原文**，判 `supported=1 / weak=0.5 / unsupported=0` |
| 引用归属错 | `unsupported` 条数。典型形态：正文用了 A 文档的数据，角标却挂在 B 文档上 |
| 必引命中 | `must_cite` 文档被正确引用的比例 |
| 论述重复率（主） | 跨章重复的 12 字论述片段占比——读者感知的「复读机」 |
| 来源复用率（参考） | 被 ≥2 章引用的来源占比。比论述重复高约 4 倍，**不能拿来下结论** |

`引用有效率` 在本架构下恒为 100%（Researcher 已丢弃无法核验的 quote），**应视为缺失指标而非满分**，已用语义支持率取代。

判官与被测模型不是同一家厂商，但仍需注意：`reasoning_effort=low` 是为速度做的让步，判官的推理深度低于生成模型；这是本轮的成本，已写进局限。

## 5. 语义抽样：为什么必须改

第一版按顺序取每章前 2 条带角标的句子，结果三档方案的支持率都是 96~97%——**每章开头第一句通常就是最直白的引用**，数字照抄、结论照抄，判它 supported 没有任何信息量。

改成按"脱离原文的风险"排序取头部：

- 含推断词（意味着/因此/表明/将成为…）**+3**
- 含带量纲数字（% / GWh / 亿元 / 个百分点…）**+2**
- 长度 ≥40 字 **+1**

效果：A 组语义支持率 96.3% → **92.2%**，`unsupported` 从 3 条涨到 **16 条**，而且抓到的都是真问题（§6）。

代价要说清楚：**换了抽样算法，本轮的语义支持率与 v4 及之前的批次不可直接比较。**

## 6. 单 Agent 到底差在哪：引用归属错乱

A 组 16 条不支持里，形态高度一致——**数据是对的，挂错了出处**：

> 「2025年工商业储能新增装机约8.4GWh，同比增长62%」`[^doc_07_region_cig]`
> —— 8.4GWh 出自 `doc_04_scale_cig`，doc_07 只讲区域分布

> 「当前磷酸铁锂在新型储能装机中的占比达到96.5%」`[^doc_12_tech_na]`
> —— doc_12 讲钠电示范阶段，96.5% 出自 doc_11

> 「2025年新增储能项目中约45%由非头部企业承接」`[^doc_12_tech_na]`
> —— 该数据出自 doc_09 竞争格局

这不是"写得不好"，是**读者照着角标去查会查不到**。B 组只有 1 条同类问题，因为它的每章检索和写作共享同一个素材包，角标只能落在本章真实用到的来源上。

**所以多 Agent 的收益不是"更聪明"，是"引用归属正确"。** 这解释了为什么覆盖率涨 7.7pp、语义支持率涨 7.4pp 会同时出现：单 Agent 把 14 个片段混在一起写 5 章，跨文档串数据是必然的。

## 7. Reviewer 为什么仍然没有收益

打回数据（v6，C 组 40 个任务）：152 个 review 节点中 21 个被打回，缺陷几乎全是"数字与原文不符"。

它确实修好了那 21 处。但**它看不到"本章漏了哪个要点"**——`must_cover` 是评测集的标注，Reviewer 没有这个信息，也就无法朝覆盖率努力。

更要紧的是：在它本该擅长的语义支持率上，B 99.7% → C 98.9%，**反向 0.8pp**。合理解释是打回重写会重新生成整章，新写的版本可能引入新的归属错误——修一个、坏一个，净收益为零。

所以对 Reviewer 的判断是：**当前设计下不值得保留**。它带来 +49% 成本、+7 秒耗时、更大的方差，以及统计上看不出来的质量提升。

如果要救它，方向不是"更严格地打回"，而是把它改成**覆盖检查器**：给它章节应该覆盖的要点（而不是没有的信息），让它回答"这章漏了什么"。这是一个不同的产品决策，不该混在"修 bug"里做。

## 8. 局限

- **判官推理档低**：为把 70 秒压到 8 秒，判官跑在 `reasoning_effort=low`。判官深度低于被测模型，绝对分数可能偏乐观。
- **语料只有 22 篇 / 79 片段**：40 个主题共享同一个知识库，主题之间的独立性有限，CI 只能算下界（真实泛化误差更大）。
- **单次重复**：n=40 的配对比较已够支撑 +7.7pp 的结论，但没有重复就无法分解"生成随机性"与"主题难度"各自贡献多少方差。
- **论述重复率 A 1.1% / B 8.7% / C 9.3%**：分章写作的真实代价。
  两次专门尝试都没降下来，且第二次（文档预算）在新指标下**显著恶化 +4.4pp**——
  而用旧的来源复用率衡量时它显示为「−1.2pp 不显著」，方向完全相反。
  根因与完整数据见 [docs/REPEAT_RATE.md](REPEAT_RATE.md)。
- **单份成本口径**：报告里的 `¥0.0055/0.0199/0.0296` 只含生成，判官另计约 ¥0.006/份。做预算时两者都要算。

## 9. 复现

```bash
cd backend
python -m app.cli doctor                     # 会分别体检生成模型与判官

cd ..
LLM_MODE=live python eval/run_eval.py --arms A,B,C --run-id v6
```

- `LLM_MODE` 必须是 `live`：评测器会拒绝 `auto/replay`，否则"重复 N 次"命中同一份缓存，等于同一次结果算 N 遍。
- 判官配置见 `.env` 的 `LLM_JUDGE_*`；换成同厂商模型只需删掉 `LLM_JUDGE_BASE_URL/API_KEY`（判官即回落到生成模型，代价是自我偏好）。
- 单例耗时 A 12s / B 18s / C 25s，判官另加 ~8s；40 主题全量约 70 分钟、¥2.75。
